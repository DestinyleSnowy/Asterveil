# 7FA4 网页加载性能分析

测量日期：2026-09-28。结论：存在明确的优化空间，优先处理首页大图、文本资源压缩和榜单串行加载。当前仓库是浏览器扩展，不包含 7FA4 网站后端；初次诊断后已实现并试验部分扩展端优化，见第 7 节。未改动线上网站服务器。

## 测量方法与边界

在 Chrome 现有登录环境下检查外网 HTTPS 8888 入口，保留当前扩展和页面功能。共采集 9 次导航：正常缓存首页两次、禁用缓存首页一次、榜单两次，以及计划、题目、模测详情、学习各一次。禁用缓存仅作用于临时测试标签，采样后已恢复。没有清空用户缓存、修改账号设置或提交题目。

使用 Navigation/Resource Timing、Paint Timing、缓冲的 LCP/布局偏移/Long Tasks，以及部分页面的 DevTools 性能计数。没有模拟低端 CPU 或慢速网络。正常缓存表示允许浏览器缓存，并非所有资源都命中缓存；题目页仍首次下载了部分字体。禁用缓存不等于首次建连，因为已有 DNS、连接和浏览器执行缓存可能仍存在。

这是当前设备和网络下的少量实验室样本，不代表所有用户的平均值或第 75 百分位，也不是优化前后 A/B 实验。没有测量真实交互 INP。未检查内网入口。原始计时汇总见 [采样数据](performance-2026-09-28.json)，不保存网页内容、成绩、源码或头像标识。

## 实测概览

单位为秒，数值四舍五入。TTFB 从导航开始到收到 HTML 首字节；FCP 是首次显示文字等内容；load 是页面 load 事件，不能代替异步业务数据就绪。

| 页面 / 缓存状态 | TTFB | FCP | DOMContentLoaded 完成 | load | 补充观察 |
| --- | ---: | ---: | ---: | ---: | --- |
| 首页，正常缓存，第 1 次 | 0.134 | 0.476 | 0.653 | 7.203 | 大图请求耗时 7.049，LCP 9.576 |
| 首页，正常缓存，第 2 次 | 0.126 | 0.356 | 0.422 | 2.120 | 大图请求耗时 1.931，LCP 4.684 |
| 首页，禁用缓存 | 0.124 | 4.072 | 4.918 | 5.970 | 大图请求耗时 5.691，LCP 8.128 |
| 我的榜单，第 1 次 | 0.055 | 0.164 | 0.141 | 0.150 | 成绩 JSON 到 1.756 才返回 |
| 我的榜单，第 2 次 | 0.061 | 0.164 | 0.131 | 0.143 | 成绩 JSON 到 0.989 返回 |
| 计划 | 0.045 | 0.160 | 0.132 | 0.154 | 随后读取 26 个日期接口 |
| 题目详情 | 0.195 | 0.276 | 0.372 | 0.862 | LCP 0.612，另有后续字体请求 |
| 模测详情 | 0.074 | 0.192 | 0.144 | 0.177 | LCP 0.192 |
| 学习 | 0.322 | 0.424 | 0.915 | 0.940 | 入口经过跳转，不能直接归因为后端计算慢 |

FCP 可能晚于 load：load 标记的是加载事件，不保证对应内容已呈现在屏幕。榜单更明显，load 很快结束，核心业务数据仍未完成。数据中的 decoded 字节包括缓存资源；不能把它们都当成本次网络流量。

## 1. 首页大图：最高优先级

实际首屏图片路径 `/index_image/0`，响应类型 PNG，原图 **7050 × 4962**，约 3500 万像素，文件 **2,410,474 字节**。当前显示尺寸约 **649 × 457**。按 2 倍像素密度准备约 1300 像素宽的图片，也远小于目前原图。

两次正常缓存导航都观察到约 2.41 MB 的完整传输，不是只检查更新的几百字节响应。说明至少在本次路径和会话中，重复访问没有避免图片正文传输。没有取得该认证图片的完整响应头，不能据此断言是哪条缓存配置造成；未登录 HEAD 返回 HTML，已排除，不把它当作图片响应的证据。

禁用缓存时，此图约占 HTML 和子资源可见传输总量 4.12 MB 的 58%。它从请求完成到成为最终 LCP 元素还有约 2.16～2.57 秒延迟。尺寸很大意味着潜在解码、缩放和绘制成本，但这部分尚未通过完整渲染追踪归因，不能全算作解码耗时。后续试验发现测试标签失焦会影响帧回调，早期 LCP 样本也可能受此影响，不能据此承诺解码优化能节省这些秒数。按 RGBA 四字节粗算，一张完整像素缓冲约 133 MiB；这是理论体量，不是实测内存占用。

建议网站提供 650 / 1300 / 2000 像素等规格的缩略图，按布局与屏幕密度选择，保留原图供需要时打开。图片若包含文字或线条，应比较 PNG、无损 WebP 和适当质量的有损格式，先验证清晰度；不能承诺仅靠改格式就达到某个体积。配套设置尺寸或纵横比、图片版本标识以及适合其访问权限的缓存策略。

这张图在首屏，不应为了减少 load 时间直接懒加载或隐藏。对于 LCP 图片，延后请求会增加资源发现延迟。[LCP 优化文档](https://web.dev/articles/optimize-lcp)、[响应式图片](https://web.dev/learn/design/responsive-images)。

扩展能调整加载优先级或解码提示，但无法在第一次下载之前把服务器的 2.41 MB 响应变成缩略图。先下载再用 Canvas 缩放，首次网络开销依然存在；缓存本地缩略图还必须解决图片更新与账号隔离。因此不把这类方案当作已经实现的加速。

## 2. 文本资源未压缩：确定性很高的全站收益

禁用缓存的首页资源中，主要 CSS / JS 的 encodedBodySize 与 decodedBodySize 相同；公开静态资源在发送 Accept-Encoding 后，响应仍无 Content-Encoding。五份实际文件的离线压缩结果如下，KB 使用十进制：

| 资源 | 现有原始大小 | gzip level 6 | Brotli quality 5 |
| --- | ---: | ---: | ---: |
| Semantic UI CSS | 628.5 KB | 103.2 KB | 93.3 KB |
| Semantic UI JS | 275.7 KB | 71.3 KB | 63.3 KB |
| jQuery | 86.9 KB | 30.4 KB | 29.7 KB |
| Chart.js | 199.6 KB | 67.7 KB | 64.8 KB |
| 日期适配器 | 50.8 KB | 11.8 KB | 10.9 KB |
| 合计 | **1241.6 KB** | **284.4 KB** | **262.0 KB** |

Brotli 结果比原始体积减少约 **78.9%**，gzip 减少约 **77.1%**。这是文件体积实验，不等于网页耗时也会缩短 79%。压缩需要由网站服务器或反向代理提供，并正确处理 Content-Encoding、Vary 和缓存变体。[文本压缩说明](https://web.dev/articles/codelab-text-compression-brotli)。

首页冷加载中，Semantic UI CSS 下载耗时 **3.67 秒**，结束于导航后 3.87 秒，FCP 为 4.07 秒。它位于首屏关键路径，优先压缩这份文件比微调几毫秒的浏览器逻辑更有价值。HTML、JSON 和其他文本也值得核对压缩，但带认证和敏感内容的响应需要结合服务器现有策略配置。

静态 CSS / JS 已有 `public, max-age=31536000`，复访多数命中缓存，这部分做得有效。问题不是“所有缓存都没开”。保持版本化资源和长缓存即可，不需要扩展再建立一套重复的永久缓存。

## 3. 公共资源装载偏重

首页载入约 **659 KB CSS** 和 **629 KB JS**（解码后文件大小，含缓存）。首页有 9 份阻塞样式表和 1 份阻塞脚本。首页、榜单和模测详情均载入 Chart.js 与日期适配器；观察到的榜单最终 DOM 没有 canvas，而题目详情存在 3 个 canvas，说明图表库确实在某些页面有用途。

网站侧可按路由和实际组件加载图表、编辑器、公式与代码高亮资源。Chart.js 加适配器原始大小约 250 KB；是否可以从每个无 canvas 页面移除，仍需检查动态功能，而不只是静态 DOM。

不建议扩展直接拦截这些库，或把所有 script 强行加 async/defer。站点内联脚本依赖 jQuery 与 Semantic UI 的顺序，错误重排会影响下拉菜单、提交、表单和异步表格。

## 4. 榜单：页面外壳快，核心数据串行加载

实测链路如下：

1. 页面外壳完成约 0.15 秒。
2. 约 0.15 秒开始请求 `/progress/contest_table/html`，约 0.31～0.33 秒返回约 255 KB 表格 HTML。
3. 插入 HTML、执行初始化后，约 0.54～0.57 秒才请求 `/progress/contest_table/json`。
4. 成绩 JSON 约 86 KB，返回于 0.99～1.76 秒；随后观察到 103～158 ms 长任务。

页面含约 4179 个元素、106 行和 1484 个单元格。实际内联代码会逐个更新排名/分数，再 `tbody.empty()` 后逐行 append；成绩单元格已有部分差量检查，但排序行仍整体移出再插入。这说明可以继续优化，不能说整张表完全没有增量处理。

优先方案是首个表格响应就携带显示所需的成绩，或在知道同一参数时并行启动两类请求。后续更新复用现有行、只移动顺序确实变化的行，并批量修改。榜单接口耗时有明显波动；当前计时无法区分后端计算、排队和网络传输，若有服务器权限，应补充 Server-Timing 与查询日志再决定是否优化数据库。

自动更新当前关闭，代码仍设置了 20ms 的定时器，但回调立即检查开关退出；它不等于每秒都在重绘 50 次，更不是本次首屏的主要瓶颈。可以在网站侧改为开启时注册、关闭时取消，自动滚动使用 requestAnimationFrame。扩展不应接管全部计时器或悄悄降低成绩刷新频率。

## 5. 计划与其他页面

计划页一次请求 **26 个 `/user_plan` 日期接口**，单个响应往往只有几百字节。这次请求基本在约 0.3 秒返回，页面 LCP 约 0.41 秒，暂时没有成为主要等待项。高延迟网络下，合并为日期范围接口可减少请求和后端调用开销，优先级低于大图、压缩和榜单。

题目详情本次约 0.28 秒显示内容、LCP 约 0.61 秒，记录到 4 个 59～126ms 的长任务。存在图表、公式或编辑器等资源，但本次没有 CPU 调用栈，不能把这四个任务直接归因给某一个库。学习页约 0.42 秒显示内容、0.94 秒 load，模测详情则约 0.19 秒显示主要内容。现有样本没有显示这些页面需要先做侵入式重写。

## 6. 仅用 Asterveil 能做多少

| 改动 | 实现位置 | 预期收益 / 边界 |
| --- | --- | --- |
| Gravatar 拦截和本地头像 | 扩展，已有 | 实页 248 个头像已替换；计时里仍可出现被取消或阻止的资源记录，不能把记录数量等同于真实下载次数 |
| 大图按尺寸提供版本 | 网站图片接口 | 首页最值得处理；扩展无法免除首次原图下载 |
| Brotli / gzip | 网站或反向代理 | 五份文件离线体积可减少约 79%，不改变页面行为 |
| 按需加载公共库 | 网站模板与组件 | 减少首次传输和初始化；必须检查依赖顺序 |
| 合并榜单与计划数据 | 网站接口与页面 | 缩短串行等待、减少碎片请求；扩展不能凭空提供新接口 |
| 屏幕外区域延迟渲染 | 扩展可实验 | 可用 content-visibility 对独立长内容区域做 A/B；对 table、固定表头、日期跳转和打印需要专门验证，不会减少网络传输 |
| 图片解码提示、保留尺寸 | 扩展可实验 | 可能改善局部绘制或位移，收益需要复测；不能代替缩图和压缩 |

`content-visibility: auto` 可以让浏览器跳过部分屏外布局和绘制，但需要正确划分区域并保留合理尺寸。[官方说明](https://web.dev/articles/content-visibility)。本次没有测出足以支持将它全站启用的收益，尤其不能直接改表格 display 或逐行隐藏来换取虚假的首屏提升。

建议实施顺序：**压缩文本资源 + 首页缩略图 → 榜单首屏数据链路 → 公共库按需加载 → 计划请求合并 → 有实测收益的扩展端渲染优化**。前两项证据最充分，实施后应在相同页面、网络和缓存条件下多次复测 FCP、LCP、业务数据就绪时间及交互，而不是只看 load 事件提前了多少。

## 7. 扩展端实施与试验

按用户确认的网络条件处理：`in` 无需访问公网，网站自身资源可用；`jx` 也不使用 Gravatar。保持现有双入口 Gravatar 官方域名和镜像图片拦截，头像由本地 SVG 生成。没有增加 CDN、外部图片服务、资源代理或新的权限。

已实现默认开启的“首页加速”模块，仅匹配 `/`：

- 同入口 `/index_image/:id` 图片缺少明确设置时，添加 `decoding="async"` 和 `fetchpriority="high"`；不替换地址、不改变清晰度、不额外下载或持久缓存。显式的 sync、low、lazy 等原站设置保持不变。优先级只是提示，解析器可能已发起请求，未测得可靠的网络加载提升。
- 对首页独立卡片使用 `content-visibility: auto`。首次正常布局后由 ResizeObserver 读取内容区高度，保留实际滚动范围，再减少屏外渲染。没有拆分表格或移除行；悬停和内部焦点时恢复完整绘制，打印始终正常绘制。限制在至少 768px 的屏幕宽度，避免窄屏原有溢出被包含规则改变。
- `local-avatars` 和图片提示允许在设置读取完成后提前启动，随 HTML 解析处理新图片；其他模块仍等待 DOM 就绪。关闭和上下文清理时释放观察器、样式及仍由模块持有的属性。

### 验证与收益边界

真实外网首页注入同一实现进行开关对比：图片 URL、尺寸、表格和行数不变；桌面页面滚动高度均为 5082px、宽度均为 2550px。390px 视口下关闭卡片延迟渲染后，开关前后原有滚动高度均为 15203px、宽度均为 412px；未顺带修改网站原有窄屏布局。测试了首页原生选项卡、滚动到屏外卡片以及打印样式。

前台标签页内，重复 16 次小幅调整容器宽度并读取布局，交替开关两轮，各轮三次样本如下，单位 ms：

| 轮次 | 关闭 | 开启 |
| --- | --- | --- |
| 1 | 93.3 / 104.3 / 88.9 | 87.8 / 73.4 / 84.8 |
| 2 | 80.1 / 113.4 / 110.7 | 61.7 / 63.6 / 64.8 |

这表明特定重复布局场景的工作量有所下降，但样本波动明显，且是微基准，不是首次加载 A/B。不能将其换算为整站加载提速比例，也没有新的可靠 FCP/LCP 改善结论。

本地夹具使用真实模块与运行时，在页面尾部加入 650ms 延迟的阻塞脚本：旧时机的头像约 677ms 才替换，提前启动后约 43～53ms 即替换，且 readyState 仍为 loading。`jx`、`in` 两套目标配置各通过 24 项断言，覆盖阶段启动、动态图片、来源边界、显式属性保留、开关清理、旧设置补齐及异步加载取消。夹具禁止远程图片，测试的是启动与 DOM 行为，不能代替实际内网联网和安装后的 DNR 验收。

首页原图仍为 2.41MB，网站文本压缩和榜单串行接口也未改变。这些主要等待项仍需要网站侧配合；本次扩展优化主要减少本地渲染与头像显示等待。
